title: Migration from v8 to v9
description: Learn how to migrate from next-safe-action version 8 to version 9, with an automated codemod and a step-by-step checklist for AI coding agents.
---

Version 9 is a cleanup release. It raises the minimum supported versions of Next.js, React, and Node.js, removes the APIs that were deprecated during v8, ships built-in [route handlers](/docs/advanced/route-handlers), and fixes how framework signals are handled during `cacheComponents` prerenders.

For most apps, the upgrade is two commands: update the dependencies, then run the codemod. The codemod rewrites the removed APIs for you and reports everything it cannot change safely.

<Callout title="Using an AI coding agent?">
Point your agent to the [For AI agents](#for-ai-agents) section. It is a deterministic checklist with detection commands, exact transformations, and done criteria for every change. The raw Markdown of this page is available at `https://next-safe-action.dev/docs/migrations/v8-to-v9.md`.
</Callout>

## Breaking changes at a glance

Every breaking change has a stable rule id. The codemod uses the same ids in its output, and each id links to its section on this page.

| Rule id | Change | Replacement | Codemod |
|---|---|---|---|
| [`V9-01`](#v9-01) | `next-safe-action/stateful-hooks` entry point removed | Import `useStateAction` from `next-safe-action/hooks` | Full |
| [`V9-02`](#v9-02) | Deprecated type aliases removed (`HookSafeActionFn`, `HookSafeStateActionFn`, `DVES`, `StateServerCodeFn`, `SafeActionUtils`) | The current names, same generic parameters | Full |
| [`V9-03`](#v9-03) | `.schema()` client method removed | `.inputSchema()` | Partial: rewrites calls on proven safe action clients, reports the rest |
| [`V9-04`](#v9-04) | Next.js >= 15.1.0, React >= 19.0.0, Node.js >= 18.18, adapters require next-safe-action >= 9.0.0 | Update your dependencies | Reports only, never edits `package.json` |

Apart from these changes and the [behavior change](#behavior-changes) for prerender signals, the public API of v9 is the same as v8.7.

## Upgrade in 5 steps

<Steps>
<Step>

### Update dependencies

Install next-safe-action v9:

```package-install
npm install next-safe-action@9
```

If you use any first-party adapter, update it in the same step. Every adapter release that supports v9 requires `next-safe-action` >= 9.0.0, so the core package and the adapters must move together. Install only the adapters you use:

```package-install
npm install @next-safe-action/adapter-react-hook-form@latest @next-safe-action/adapter-tanstack-query@latest @next-safe-action/adapter-better-auth@latest
```

If your app runs on Next.js older than 15.1.0 or React older than 19.0.0, upgrade them too:

```package-install
npm install next@^15.1.0 react@^19 react-dom@^19
```

TypeScript users should also install `@types/react@^19` and `@types/react-dom@^19` as dev dependencies. See [New minimum requirements](#v9-04) for the full list.

<Callout title="Coming from Next.js 14?">
Upgrading Next.js from 14 to 15 is a separate migration with its own breaking changes (async request APIs, caching defaults, React 19). Follow the [Next.js 15 upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-15) first, then come back to this guide. If you cannot upgrade Next.js yet, stay on next-safe-action v8.
</Callout>

</Step>
<Step>

### Commit your work

The codemod refuses to write files when the git working tree has uncommitted changes (untracked files count too), so you can always review and revert what it did. Commit (or stash) the dependency update:

```bash
git add -A
git commit -m "chore: upgrade next-safe-action to v9"
```

</Step>
<Step>

### Run the codemod

Preview the changes first. `--dry` writes nothing:

```bash
npx @next-safe-action/codemod@latest v9 --dry
```

Then apply them:

```bash
npx @next-safe-action/codemod@latest v9
```

Run both commands from your project root. Without arguments, the codemod scans the current directory. To limit the run to specific files or directories, pass them as arguments, for example `npx @next-safe-action/codemod@latest v9 src`. The V9-04 requirement checks read the `package.json` files that are inside the scanned paths, so a run limited to `src` cannot check your dependencies: the report then has an `unknown` entry with the file `(not found)` that tells you to run from the project root. See the [codemod reference](#codemod-reference) for all flags.

</Step>
<Step>

### Resolve manual items

The codemod prints a list of manual items: places it found but could not change safely. Each item has a rule id, a file and line, a reason, a suggested fix, and a link to the matching section of this page. Fix each one by hand. Many items point at text in comments, strings, or Markdown files: change what refers to next-safe-action and ignore the rest (for example a `.schema()` call of another library).

</Step>
<Step>

### Verify

Type check, lint, test, and build your app:

```bash
npx tsc --noEmit
npm run lint
npm test
npm run build
```

Use your own script names. TypeScript reports every leftover use of a removed API in typed code, so a clean `tsc --noEmit` is the strongest signal that the migration is complete. Review `git diff`, then commit.

</Step>
</Steps>

## For AI agents [#for-ai-agents]

This section is a deterministic procedure for AI coding agents. Humans can use it too, as a checklist. Follow the steps in order. Every step has a command, an expected result, and a done criterion.

Machine-readable versions of the docs:

- This page as Markdown: `https://next-safe-action.dev/docs/migrations/v8-to-v9.md`
- Index of all pages: `https://next-safe-action.dev/llms.txt`
- All pages in one file: `https://next-safe-action.dev/llms-full.txt`

Any docs page is available as Markdown when you append `.md` to its URL.

### Ground rules

- The migration does not change application behavior. It renames imports, types, and one method, and it updates dependency versions. Do not refactor anything else.
- Use the package manager the project already uses. Detect it from the lockfile: `package-lock.json` (npm), `pnpm-lock.yaml` (pnpm), `yarn.lock` (yarn), `bun.lock` or `bun.lockb` (bun). In a monorepo, run the install command in the workspace that depends on `next-safe-action` (for example `pnpm --filter <app> add ...`).
- Never rename a `.schema(` call unless its receiver is a next-safe-action client. Other libraries have `.schema()` methods too.
- Never pass `--force` to the codemod to get past a dirty working tree unless the user approved it. Commit or stash first, or ask.
- Write codemod reports outside the repository (for example in `$TMPDIR`). A report file inside the repository is an untracked file, which makes the working tree dirty, and the codemod then refuses to run.
- With `--json`, the report is the only thing on stdout. The codemod writes its log lines and errors to stderr. Check the exit code before you parse the report: on exit code `1`, stdout is empty.

With pnpm, use `pnpm ls` with the same arguments. With yarn, use `yarn why <package>`. With bun, use `bun pm ls`.

Required minimums:

|---|---|
| Node.js | 18.18 |
| `next` | 15.1.0 |
| `react`, `react-dom` | 19.0.0 |
| `next-safe-action` | 9.0.0 |
| `@next-safe-action/adapter-react-hook-form` | 3.0.0 |
| `@next-safe-action/adapter-tanstack-query` | 0.2.0 |
| `@next-safe-action/adapter-better-auth` | 0.2.0 |

Update commands. Add only the adapters that are already dependencies of the project:

| Package manager | Command |
|---|---|
| npm | `npm install next-safe-action@9 @next-safe-action/adapter-react-hook-form@latest` |
| pnpm | `pnpm add next-safe-action@9 @next-safe-action/adapter-react-hook-form@latest` |
| yarn | `yarn add next-safe-action@9 @next-safe-action/adapter-react-hook-form@latest` |
| bun | `bun add next-safe-action@9 @next-safe-action/adapter-react-hook-form@latest` |

If `next` is older than 15.1.0, stop and tell the user: a Next.js 14 to 15 upgrade is a separate migration (see the [Next.js 15 upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-15)). If only `react`/`react-dom` are below 19.0.0 on Next.js >= 15.1.0, install `react@^19 react-dom@^19` and, for TypeScript projects, `@types/react@^19 @types/react-dom@^19`.

**Done when:** every package in the table meets its minimum, and the package manager reports no peer dependency errors for `next-safe-action` or its adapters. Then commit the dependency update.

### Step 2: Run the codemod with a JSON report

Preview, with the report outside the repository:

```bash
npx @next-safe-action/codemod@latest v9 --dry --json > "${TMPDIR:-/tmp}/nsa-v9-dry.json"
```

Apply, after the working tree is clean:

```bash
npx @next-safe-action/codemod@latest v9 --json > "${TMPDIR:-/tmp}/nsa-v9.json"
```

The report has four arrays. Consume them in this order:

1. `environment`: one entry per check (rule `V9-04`), including the checks that pass and the running Node.js. Ignore entries with `status: "ok"`: their `fix` is an empty string. For `status: "upgrade"`, apply `fix`, then commit: for `next-safe-action` and the adapters it is an install command for your package manager, for `next` it suggests the Next.js upgrade codemod, and for `react`, `react-dom`, and Node.js it describes the change to make. For `status: "unknown"`, the codemod could not read a version (a `workspace:` or `catalog:` range, a tag, a `||` or `>` range, or an adapter that is not installed). Check that package by hand with the commands in Step 1. An entry with `file: "(not found)"` means that the scanned paths had no `package.json` that depends on next-safe-action or an adapter, so no dependency check ran: run the codemod again from the project root, or pass the path of that `package.json`.
2. `changes`: the edits the codemod made (`rule`, `file`, `line`, `before`, `after`). Review them with `git diff`. No action is needed unless an edit looks wrong.
3. `manual`: places the codemod found but did not change. For each entry, open `file` at `line`:`column`, read `why`, apply `fix`, and use the section linked in `docs` (`#v9-01` to `#v9-04`) for the exact transformation.
4. `skipped`: `{ file, reason }` entries for what the codemod could not process: a source file with a syntax error (not transformed, but its leftovers are in `manual`), a source file that the codemod failed to analyze or read (not transformed), a path argument that is a symlink (not followed), or a `tsconfig.json` that failed to load (its files were analyzed without its path aliases, so expect more `manual` items). Fix the cause and run the codemod again, or check those files by hand with the detection commands in Step 3.

To list the unresolved environment entries and the manual items in a compact form (requires `jq`):

```bash
jq -r '.environment[] | select(.status != "ok") | "\(.status) \(.file) \(.package) \(.found) \(.fix)"' "${TMPDIR:-/tmp}/nsa-v9.json"
jq -r '.manual[] | "\(.rule) \(.file):\(.line):\(.column) \(.fix)"' "${TMPDIR:-/tmp}/nsa-v9.json"
```

The exit code is `0` even when there are manual items, so read the `manual` array instead of relying on the exit code. Exit code `1` means an error or a dirty working tree. The full format is in [Report format](#report-format).

**Done when:** the codemod ran without `--dry`, no `environment` entry has `status: "upgrade"` or an unchecked `"unknown"`, and every `manual` and `skipped` entry is resolved.

### Step 3: Check every rule

Run these checks even after the codemod, to catch anything it could not see. `rg` (ripgrep) skips files ignored by `.gitignore`, so `node_modules` and build output are not searched.

#### V9-01: `next-safe-action/stateful-hooks`

Detect:

```bash
rg -n "next-safe-action/stateful-hooks"
```

Transform: replace the module specifier `next-safe-action/stateful-hooks` with `next-safe-action/hooks`. The imported names do not change. This applies to every form: `import`, `import type`, `export ... from`, `import()`, `require()`, `vi.mock()`, `jest.mock()`, and any path alias or text that names the module.

```ts
// before
import { useStateAction } from "next-safe-action/stateful-hooks";
// after
import { useStateAction } from "next-safe-action/hooks";
```

False positives: none. Historical text, such as a changelog, can stay as is.

**Done when:** the search returns no hits outside historical text.

#### V9-02: removed type aliases

Detect:

```bash
rg -nw "HookSafeActionFn|HookSafeStateActionFn|DVES|StateServerCodeFn|SafeActionUtils"
```

Transform: rename the identifier in the import and at every use. Keep the generic arguments as they are: they have the same parameters in the same order.

| Removed | Replacement | Import from |
|---|---|---|
| `HookSafeActionFn` | `SingleInputActionFn` | `next-safe-action/hooks` |
| `HookSafeStateActionFn` | `SingleInputStateActionFn` | `next-safe-action/hooks` |
| `DVES` | `ValidationErrorsFormat` | `next-safe-action` |
| `StateServerCodeFn` | `StatefulServerCodeFn` | `next-safe-action` |
| `SafeActionUtils` | `ActionCallbacks` | `next-safe-action` |

```ts
// before
import type { DVES as Format, SafeActionUtils } from "next-safe-action";
// after
import type { ValidationErrorsFormat as Format, ActionCallbacks } from "next-safe-action";
```

For an aliased import, rename only the imported name and keep the local alias. For a namespace import (`import type * as NSA from "next-safe-action"`), rename the member access (`NSA.DVES` becomes `NSA.ValidationErrorsFormat`). For a re-export (`export type { DVES } from "next-safe-action"`), rename the exported name, or keep the old public name with `export type { ValidationErrorsFormat as DVES } from "next-safe-action"` if other packages depend on it. The codemod takes the first option.

False positives: an identifier with one of these names that is declared locally or imported from another package. Rename only identifiers that come from `next-safe-action` or `next-safe-action/hooks`, directly or through a re-export.

**Done when:** every remaining hit is declared somewhere else than next-safe-action.

#### V9-03: `.schema()` method

Detect:

```bash
rg -n "\.schema\s*[(<]|\[\s*['\"\`]schema['\"\`]\s*\]\s*[(<]"
```

Transform: rename `.schema(` to `.inputSchema(` (and `client["schema"](` to `client["inputSchema"](`) when the receiver is a next-safe-action client. The arguments do not change, including async schema factories.

```ts
// before
export const action = actionClient.schema(schema).action(async ({ parsedInput }) => {});
// after
export const action = actionClient.inputSchema(schema).action(async ({ parsedInput }) => {});
```

A receiver is a next-safe-action client when it is the return value of `createSafeActionClient()`, or the result of calling a client method on one (`.use()`, `.useValidated()`, `.metadata()`, `.inputSchema()`, `.bindArgsSchemas()`, `.outputSchema()`). Calls after `.action()` or `.stateAction()` are not on a client. Trace the receiver back to its declaration, through imports and re-exports, to decide. Calls often sit on their own line in a method chain, so read the lines above each hit.

False positives: this pattern also matches `.schema()` methods of other libraries (validation libraries, ORMs, query builders, API clients). Leave those unchanged.

**Done when:** every remaining hit has a receiver that is not a next-safe-action client, and `tsc --noEmit` passes. In typed code, a leftover call fails with `Property 'schema' does not exist on type 'SafeActionClient<...>'`.

#### V9-04: requirements

Covered by Step 1. **Done when:** the Step 1 criterion holds.

Run the project's own scripts. Typical commands:

npm test

## Removed `stateful-hooks` entry point [#v9-01]

**What changed:** the `next-safe-action/stateful-hooks` entry point is removed.

**Why:** the entry point existed to keep code that needs React 19 (`useActionState`) away from React 18 builds. Since v8.3.0, `useStateAction` is exported from `next-safe-action/hooks`, and `stateful-hooks` was only a re-export kept for backward compatibility. Now that v9 requires React 19, a separate entry point has no purpose.

```ts title="v8"
import { useStateAction } from "next-safe-action/stateful-hooks";
```

```ts title="v9"
import { useStateAction } from "next-safe-action/hooks";
```

**Codemod:** full. It rewrites every string literal that is exactly `next-safe-action/stateful-hooks` (also a template literal without expressions) and keeps the quotes. That covers static imports, type imports, re-exports, dynamic `import()`, `require()`, and `vi.mock()` and `jest.mock()` calls. When the same file already has a named `next-safe-action/hooks` import of the same kind (both `import` or both `import type`), the codemod merges the names into it, without duplicates, and removes the old import line.

A `vi.mock()` or `jest.mock()` call with a factory is rewritten too, and also reported as a manual item: the factory used to replace only `next-safe-action/stateful-hooks`, and it now replaces all of `next-safe-action/hooks`, so every hook that it does not return (for example `useAction`) is `undefined` in that test file. Spread the real module into the factory, with `...(await vi.importActual("next-safe-action/hooks"))` or `...jest.requireActual("next-safe-action/hooks")`. The codemod reports this item only on the run that rewrites the specifier. A mock call without a factory needs no change.

**Manual steps:** none for the code above, apart from the mock factories described above. The codemod reports every other mention as a manual item: partial strings, comments, and files that are not JavaScript or TypeScript (for example Markdown, MDX, Vue, Svelte, or Astro).

## Removed deprecated type aliases [#v9-02]

**What changed:** five type aliases that were deprecated in v8 are removed.

| Removed | Replacement | Import from |
|---|---|---|
| `HookSafeActionFn` | `SingleInputActionFn` | `next-safe-action/hooks` |
| `HookSafeStateActionFn` | `SingleInputStateActionFn` | `next-safe-action/hooks` |
| `DVES` | `ValidationErrorsFormat` | `next-safe-action` |
| `StateServerCodeFn` | `StatefulServerCodeFn` | `next-safe-action` |
| `SafeActionUtils` | `ActionCallbacks` | `next-safe-action` |

**Why:** the new names describe what the types are. The old names were aliases kept only for backward compatibility. The replacements take the same generic parameters, in the same order.

```ts title="v8"
import type { HookSafeActionFn } from "next-safe-action/hooks";
import type { SafeActionUtils } from "next-safe-action";
```

```ts title="v9"
import type { SingleInputActionFn } from "next-safe-action/hooks";
import type { ActionCallbacks } from "next-safe-action";
```

`MiddlewareResult` is not affected: its signature is the same as in v8.

**Codemod:** full. Renames are import-aware: the codemod changes an identifier only when it traces back to next-safe-action, and it leaves a local type that has the same name alone. It handles:

- Imports, `import type`, inline `type` specifiers, and every use of the name. An aliased import (`DVES as Format`) keeps its local alias.
- Namespace access (`nsa.DVES`) and `import("next-safe-action").DVES`.
- Barrel files and re-exports (`export { DVES } from "next-safe-action"`, `export { X }`), including the files that import the name from the barrel.
- Files that already import the new name: the old specifier is removed. If the new name is already used for something else in the file, the codemod writes `ValidationErrorsFormat as DVES` and keeps the old local name.

An un-aliased re-export changes the public export name of your module (`DVES` becomes `ValidationErrorsFormat`). Files inside the scanned paths that import it are updated, but consumers outside the scanned paths, such as other packages, are not.

**Manual steps:** none for names that the codemod can trace. It reports every other mention as a manual item: names it cannot trace to a declaration, comments, strings, and text in Markdown or MDX docs.

## Removed `.schema()` method [#v9-03]

**What changed:** the `.schema()` method of the safe action client is removed.

**Why:** v8 renamed `.schema()` to `.inputSchema()` to make the difference with `.outputSchema()` clear, and kept `.schema()` as a deprecated alias. See the [v7 to v8 migration guide](/docs/migrations/v7-to-v8#-schema-method-renamed-to-inputschema).

```ts title="v8"
export const updateUser = authActionClient
	.schema(async (prevSchema) => prevSchema.extend({ name: z.string() }))
	.action(async ({ parsedInput }) => {
		/* ... */
	});
```

```ts title="v9"
export const updateUser = authActionClient
	.inputSchema(async (prevSchema) => prevSchema.extend({ name: z.string() }))
	.action(async ({ parsedInput }) => {
		/* ... */
	});
```

**Codemod:** partial. The codemod renames a `.schema()` call (also `.schema<T>()` and `client["schema"]()`) only when it can prove that the receiver is a next-safe-action client. The proof is a chain that starts at `createSafeActionClient()` from `next-safe-action`, or at a declaration typed `SafeActionClient`, and continues only through the client methods `.use()`, `.useValidated()`, `.metadata()`, `.inputSchema()`, `.bindArgsSchemas()`, `.outputSchema()`, and `.schema()`. The codemod follows the receiver across files with TypeScript symbol resolution: variables, aliases, `tsconfig.json` paths, barrel files, `export *`, namespace imports, default exports, and object properties. JavaScript files are analyzed too. When `next-safe-action` is installed, the codemod also accepts a receiver whose type is `SafeActionClient`, which covers wrapper functions.

A receiver that the codemod cannot decide becomes a manual item (for example the result of a wrapper function when `next-safe-action` is not installed, a parameter without a `SafeActionClient` type, a value typed `any`, or a dynamic value). `.schema()` calls that are provably not on a client (other libraries, calls after `.action()`) are left alone and not reported.

**Manual steps:** for each manual item, check that the receiver is a next-safe-action client and rename the call to `.inputSchema()`. Ignore the item otherwise. In TypeScript code, `tsc --noEmit` reports every call that is left.

## New minimum requirements [#v9-04]

**What changed:**

| Requirement | v8 | v9 |
|---|---|---|
| Next.js | >= 14.0.0 | >= 15.1.0 |
| React and React DOM | >= 18.2.0 | >= 19.0.0 |
| Node.js | >= 18.17 | >= 18.18 |

All first-party adapters now require `next-safe-action` >= 9.0.0, Next.js >= 15.1.0, and Node.js >= 18.18. Each adapter that has a React peer dependency requires version 19 too: the React Hook Form adapter needs `react` and `react-dom` >= 19.0.0, the TanStack Query adapter needs `react` >= 19.0.0 (it has no `react-dom` peer), and the Better Auth adapter has no React peer. These are the first adapter releases for v9:

| Adapter | First release for v9 | Previous `next-safe-action` requirement |
|---|---|---|
| `@next-safe-action/adapter-react-hook-form` | 3.0.0 | >= 8.1.10 |
| `@next-safe-action/adapter-tanstack-query` | 0.2.0 | >= 8.1.10 |
| `@next-safe-action/adapter-better-auth` | 0.2.0 | >= 8.4.0 |

**Why:**

- **Next.js 15.1:** next-safe-action detects `notFound()` through the `NEXT_HTTP_ERROR_FALLBACK;404` error digest, which Next.js introduced in 15.1. On Next.js 15.0.x, a `notFound()` call in an action was not detected as a navigation.
- **React 19:** the hooks use React 19's `useActionState` and `useOptimistic`. v8 had a runtime check that threw a descriptive error when `useActionState` was missing. v9 removes this check, because React 19 is now a hard requirement.
- **Node.js 18.18:** this is the minimum Node.js version of Next.js 15.1.

**Codemod:** reports only. It never edits `package.json`. It reads every `package.json` in the scanned paths that lists `next-safe-action` or a first-party adapter in `dependencies` or `devDependencies`, and checks `next`, `react`, `react-dom`, `next-safe-action`, each adapter, and `engines.node`. It also checks `.nvmrc`, `.node-version`, and the Node.js that runs the codemod. It prefers the version installed in `node_modules` over the declared range. An adapter passes when its installed release has a `next-safe-action` peer dependency of 9.0.0 or higher. The report says which checks are met. The fix text of a failed check is an install command for your package manager for `next-safe-action` and the adapters, a pointer to the Next.js upgrade codemod (`npx @next/codemod@latest upgrade latest`) for `next`, and a short instruction for `react`, `react-dom`, and Node.js. When the scanned paths have no such `package.json` (for example a run limited to `src`), the report has one `unknown` entry with the file `(not found)` instead.

**Manual steps:** update your dependencies as described in [Update dependencies](#update-dependencies). If you must stay on Next.js 14 or 15.0, stay on next-safe-action v8.

## Behavior changes [#behavior-changes]

### Prerender signals are re-thrown to Next.js

With `cacheComponents` (or the earlier `dynamicIO` flag), Next.js throws two control-flow signals while it prerenders a route:

- `HANGING_PROMISE_REJECTION`: a request data promise (for example `cookies()`) rejects when the prerender is complete.
- `NEXT_PRERENDER_INTERRUPTED`: a call such as `revalidatePath()` or `draftMode()` interrupts the prerender.

In v8, next-safe-action treated these signals as ordinary errors. They went to `handleServerError` (which logs them by default), fired the `onError` callback, and produced a `serverError` result.

In v9, they are handled like the other framework signals, which is the same set that Next.js `unstable_rethrow()` re-throws:

- The server-side `onNavigation` and `onSettled` action callbacks run with `navigationKind: "other"`.
- The signal is then re-thrown, so Next.js can handle it.
- `handleServerError` and `onError` are not called, and no `serverError` result is returned.
- `isNavigationError()` returns `true` for these signals.

**What you need to do:** usually nothing. If your `handleServerError` or `onError` code filtered these digests by hand, you can remove that code. If you relied on seeing these signals in `handleServerError` (for example, to count them), you will not see them there anymore. See [Framework navigation/errors](/docs/advanced/framework-errors) for details.

### Internal changes

The hooks no longer write React refs during render. This has no effect on the public API or on how the hooks behave.

## New features

### Built-in route handlers

next-safe-action can now expose selected actions as JSON endpoints through a Next.js catch-all Route Handler, and generate an OpenAPI 3.1 document from their schemas. The feature is built into the core package, with two new server-only entry points:

- `next-safe-action/routes`: `createRouter()`, `mergeRouters()`, and `createRouteHandlers()`.
- `next-safe-action/routes/openapi`: `generateOpenApiDocument()`.

There is nothing to migrate: your actions keep working as they are, and you can expose them over HTTP when you need it. See [Route handlers](/docs/advanced/route-handlers).

## Codemod reference [#codemod-reference]

```bash
npx @next-safe-action/codemod@latest v9 [paths...] [flags]
```

Run it from the project root. `paths` are files or directories. Without paths, the codemod scans the current directory.

### Flags

| Flag | Effect |
|---|---|
| `--dry` | Analyze and report, but write no files. Also runs on a dirty working tree. |
| `--print` | Print each changed file instead of writing it. Also runs on a dirty working tree. |
| `--force` | Write files even when the git working tree has uncommitted changes. |
| `--json` | Print a machine-readable report on stdout. See [Report format](#report-format). With `--print`, the printed files go to stderr. |
| `-h`, `--help` | Show the help. |

Without `--json`, the codemod prints a human-readable report on stdout: the changes, the manual items, the environment checks that need attention, and the skipped files. With `--json`, stdout holds only the JSON report, and a one-line summary and all errors go to stderr.

### What it does

| Rule | Action |
|---|---|
| `V9-01` | Rewrites every string literal that is exactly `next-safe-action/stateful-hooks` to `next-safe-action/hooks`: static and type imports, re-exports, dynamic `import()`, `require()`, `vi.mock()`, and `jest.mock()`. Merges the names into an existing `next-safe-action/hooks` import when there is one. Also reports each mock call with a factory, because the factory now replaces the whole `next-safe-action/hooks` module. |
| `V9-02` | Renames the removed type aliases, but only identifiers that trace back to next-safe-action. Handles aliased imports, re-exports and barrels, and namespace access. |
| `V9-03` | Renames `.schema()` (also `.schema<T>()` and `client["schema"]()`) to `.inputSchema()` on receivers that it proves are next-safe-action clients, with TypeScript symbol resolution across files (including `tsconfig.json` paths and barrel files). Receivers that it cannot decide become manual items. |
| `V9-04` | Checks the versions of Next.js, React, Node.js, next-safe-action, and the adapters. Reports problems with a fix: the install command for the detected package manager (next-safe-action and the adapters), the Next.js upgrade codemod (`next`), or a short instruction (`react`, `react-dom`, Node.js). Never edits `package.json`. |

The rewrites change only the text that needs to change. Quotes, line endings (including CRLF), and a byte order mark are kept.

After the rewrites, a text scan looks for leftovers of `V9-01` to `V9-03` in all scanned files, including Markdown, MDX, Vue, Svelte, and Astro files, and reports each one as a manual item, except those that the codemod proved unrelated. Running the codemod again changes nothing.

### Scanned files

- **Transformed:** `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, and `.cjs` files. Files that do not mention next-safe-action, a removed name, `.schema(`, `.schema<`, or `["schema"](` are not parsed.
- **Scanned for leftovers only:** `.md`, `.mdx`, `.vue`, `.svelte`, and `.astro` files. The codemod never changes them.
- **Read for the V9-04 checks:** `package.json`, `.nvmrc`, and `.node-version` files.
- **Always skipped:** the directories `node_modules`, `.git`, `.next`, and `.turbo`, even when git tracks them.
- **Inside a git repository:** files ignored by `.gitignore` are skipped, and nothing else. A tracked directory named `dist`, `build`, `out`, or `coverage` is scanned, because those can be source directories (for example the route `src/app/out/page.tsx`).
- **Outside git:** `.gitignore` is not read, so the directories `dist`, `build`, `out`, and `coverage` are skipped too.
- **Symlinks** are never followed: symlinked files inside the scanned directories are skipped, and a path argument that is a symlink is listed in `skipped`.

A path that names a regular file is always scanned. A path that does not exist is an error.

### Safety

- Without `--dry`, `--print`, or `--force`, the codemod refuses to run when the git working tree has uncommitted changes, including untracked files anywhere in the repository. You can then always review its edits with `git diff` and revert them. Use `--dry` or `--print` to preview, or `--force` to skip the check. A folder that is not a git repository is fine.
- It never edits `package.json` or lockfiles.
- It never changes `.schema()` calls that it cannot prove belong to a next-safe-action client.

### Report format [#report-format]

With `--json`, the codemod prints one JSON object on stdout. All paths are relative to the current directory.

```ts
type CodemodReport = {
	// Edits the codemod made (or would make, with --dry or --print).
	// One entry per rule and original line.
	changes: Array<{
		rule: string; // "V9-01" | "V9-02" | "V9-03"
		file: string;
		line: number; // line in the original file
		before: string; // the full original line (or lines)
		after: string; // the full changed line, "" when the line was removed (a merged import)
	}>;
	// Places the codemod found but did not change. Fix each one by hand.
	manual: Array<{
		rule: string; // "V9-01" | "V9-02" | "V9-03"
		file: string;
		line: number; // line and column in the migrated file
		column: number;
		snippet: string; // the trimmed line at that position, 200 characters at most
		why: string; // why the codemod did not change it
		fix: string; // what to do
		docs: string; // link to the matching section of this guide
	}>;
	// Dependency and runtime checks (rule V9-04), including the ones that pass.
	environment: Array<{
		rule: string; // "V9-04"
		file: string; // the checked file, "(current Node.js runtime)", or "(not found)" when no package.json was scanned
		package: string; // a package name, or "node"
		found: string; // always a string, see below
		required: string; // for example ">=15.1.0"
		status: "ok" | "upgrade" | "unknown";
		fix: string; // "" when status is "ok"
	}>;
	// Files and configs that the codemod could not process.
	skipped: Array<{
		file: string;
		reason: string; // a syntax error, an analysis or read failure, a symlink path, or a tsconfig.json that failed to load
	}>;
};
```

`environment[].status` has three values: `ok` (the requirement is met), `upgrade` (it is not met), and `unknown` (the codemod could not read a version).

`environment[].found` is always a string, and the codemod only reports packages that your `package.json` declares, so there is no missing value. It ends with `(installed)` when the version comes from `node_modules`, and with `(declared)` when it comes from the range in `package.json`. A declared package that is not installed gets the declared range, for example `^15.0.0 (declared)`. A range that the codemod cannot read (`workspace:*`, `catalog:`, a tag, a `||` or `>` range) and an adapter that is not installed have the status `unknown`. For an installed adapter, `found` also shows its `next-safe-action` peer range. For Node.js, `found` is the `engines.node` value, the content of `.nvmrc` or `.node-version`, or the running version.

### Exit codes

| Code | Meaning |
|---|---|
| `0` | Success, also when the report has manual items or unmet requirements. Also for `--help`. |
| `1` | An error occurred (for example a path that does not exist), the transform or a flag is unknown, or the git working tree is dirty (without `--dry`, `--print`, or `--force`). |

### Limitations

- It does not update dependencies. Do that yourself, see [Update dependencies](#update-dependencies).
- It does not rename `.schema()` calls on receivers that it cannot resolve. They are reported as manual items.
- It reports leftovers in comments, strings, Markdown, MDX, Vue, Svelte, and Astro files, but does not change them. Because it cannot tell what a mention in text refers to, some manual items are false positives, for example a `.schema()` call of another library in a Markdown file.
- It does not transform a file that has a syntax error. The file is listed in `skipped`, and its leftovers are listed as manual items.
- It analyzes every file before it writes any file, so a real run gives the same result as `--dry`. If the analysis of one file fails, that file is listed in `skipped` and left unchanged, and the other files are still migrated.
- Renaming an un-aliased re-export changes the public export name of that module. Consumers outside the scanned paths are not updated.
- It does not run your formatter. The edits keep the existing formatting, but a merged import can leave a line that your formatter would lay out differently (for example `useAction, useStateAction,` on one line of a multi-line import). Run your formatter after the codemod if your project checks formatting.
- It can use the types of an installed `next-safe-action`, which is what proves the receivers of wrapper functions. With v9 installed, the removed type names no longer exist in those types, so a removed name that is re-exported through an `export * from "next-safe-action"` barrel cannot be traced, and each use becomes a manual item. Direct imports from `next-safe-action` do not need the types.

## Troubleshooting [#troubleshooting]

### Peer dependency warnings or `ERESOLVE` errors after the upgrade

The package manager found a version that does not meet a requirement. The usual causes:

- An adapter was updated, but `next-safe-action` is still on v8. The adapter releases for v9 require `next-safe-action` >= 9.0.0. Install `next-safe-action@9`.
- `next`, `react`, or `react-dom` is below the new minimum. See [New minimum requirements](#v9-04).

Do not silence the warnings with `--force` or `--legacy-peer-deps`: they point at a real version mismatch.

### The adapters and the core package have mismatched versions

Update the core package and every adapter you use in the same install command (see [Update dependencies](#update-dependencies)). Then make sure there is only one copy of `next-safe-action`: `npm ls next-safe-action` (or `pnpm ls`, `yarn why`, `bun pm ls`) must show a single 9.x version. In a monorepo, every workspace must use the same major version.

### `Cannot find module 'next-safe-action/stateful-hooks'`

Import `useStateAction` from `next-safe-action/hooks`. See [V9-01](#v9-01).

### `Module '"next-safe-action"' has no exported member 'DVES'`

The same error for `HookSafeActionFn`, `HookSafeStateActionFn`, `StateServerCodeFn`, or `SafeActionUtils` means that the type alias was removed. Use the new name. See [V9-02](#v9-02).

### `Property 'schema' does not exist on type 'SafeActionClient<...>'`

Rename `.schema()` to `.inputSchema()`. See [V9-03](#v9-03).

### The codemod refuses to run

The git working tree has uncommitted changes, and untracked files count too (a report file that you wrote inside the repository is one). Commit or stash them and run the codemod again. To preview without writing files, use `--dry` or `--print`, which do not need a clean tree. Use `--force` only if you can review the result some other way.

### The codemod says `Path not found`

A path that you passed does not exist. Check the spelling and run the codemod from your project root.

### The codemod reported manual items, but the exit code is 0

This is intentional. Exit code `0` means the codemod ran correctly. Read the manual items in its output (or the `manual` array of the `--json` report) and fix them by hand.

### `handleServerError` no longer receives some errors during prerendering

These are the `HANGING_PROMISE_REJECTION` and `NEXT_PRERENDER_INTERRUPTED` framework signals, which v9 re-throws to Next.js. See [Behavior changes](#behavior-changes).

### I cannot upgrade to Next.js 15.1 or React 19 yet

Stay on next-safe-action v8, which supports Next.js >= 14 and React >= 18.2.0:

```package-install
npm install next-safe-action@8
```

Upgrade to v9 after you upgrade Next.js and React.

## What about v8?

Version 8 stays available on npm. The v8 documentation source is available on [GitHub](https://github.com/next-safe-action/next-safe-action/tree/next-safe-action%408.7.3/apps/docs/content/docs).
